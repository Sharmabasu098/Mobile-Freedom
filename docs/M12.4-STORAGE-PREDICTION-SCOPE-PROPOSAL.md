# M12.4 — Storage Prediction (Scope Proposal)

**Milestone:** M12.4 — Storage Prediction
**Status:** PROPOSAL — REVIEW REQUIRED BEFORE IMPLEMENTATION
**Branch:** `m12.4-storage-prediction`
**Base:** `main` (M12.3 merged)
**Parent milestone:** M12 — Storage Trend & Prediction

## Purpose

Extend M12.3's verified historical trend analysis with a cautious, deterministic estimate of future storage usage. A prediction must be clearly labeled as an estimate—not a guarantee—and must not imply device monitoring.

## Proposed scope

- Use only validated snapshots explicitly recorded in M12.2 Storage History.
- Reuse M12.1 snapshot validation and M12.3 chronological analysis; do not alter those milestones.
- Produce a bounded, deterministic forecast from the available history, with a clearly documented forecasting method.
- Require an explicit minimum history count and meaningful time span before forecasting. Exact thresholds must be agreed and tested before implementation.
- Return a safe insufficient-data result when history is too short, invalid, duplicate, or unsuitable for forecasting.
- Surface uncertainty/limitations and avoid presenting false precision.
- Provide forecast horizons only as explicit caller inputs within documented bounds.
- Avoid predictions for total capacity unless the data supports it; primarily estimate used storage and derive free storage only when capacity is stable and valid.
- Include tests for increasing, decreasing, unchanged, noisy/irregular history, sparse intervals, insufficient history, invalid records, duplicate IDs, zero elapsed time, capacity changes, numeric boundaries, and deterministic output.

## Proposed acceptance criteria

| ID | Requirement | PASS evidence |
|---|---|---|
| AC-01 | History integration | Forecast input comes from validated M12.2 history, with a test for integration. |
| AC-02 | Minimum data gate | Too few snapshots or insufficient elapsed time returns a non-prediction result. |
| AC-03 | Deterministic forecast | Same validated inputs and horizon yield identical output. |
| AC-04 | Method transparency | Forecast method and assumptions are documented in API/output documentation. |
| AC-05 | Trend handling | Increasing, decreasing, and unchanged usage are handled without sign/direction errors. |
| AC-06 | Irregular/noisy history | Results are tested against uneven timestamps and outlier/noisy patterns; limitations are documented. |
| AC-07 | Capacity safety | Capacity changes do not produce misleading free-space estimates; behavior is explicit and tested. |
| AC-08 | Horizon validation | Invalid or out-of-range forecast horizons fail safely. |
| AC-09 | Numeric safety | No unsafe arithmetic, NaN, Infinity, or overflow-like results are returned. |
| AC-10 | Uncertainty/limitations | Output clearly indicates estimate status and limitations; avoid unsupported confidence claims. |
| AC-11 | Regression | M12.1, M12.2, and M12.3 tests remain passing without scope weakening. |
| AC-12 | TypeScript | Type checking passes. |
| AC-13 | Production build | Production build passes. |
| AC-14 | CI | All required automated checks pass. |
| AC-15 | Scope safety | No background monitoring, scanning, filesystem mutation, cleanup, deletion, AI, or Android access is added. |

## Explicitly out of scope

- Background or continuous monitoring
- Automatic filesystem scanning
- File deletion, cleanup, or mutation
- Android/device storage access
- AI/ML model or cloud prediction
- Automatic alerts or notifications
- UI integration unless separately approved

## Safety principles

- Prediction is advisory and must never trigger an action.
- No prediction is preferable to a misleading prediction.
- Forecasts must be labeled estimates with visible assumptions and limitations.
- Do not claim the device is being monitored; snapshots are explicit historical measurements only.
- Preserve user control and privacy.

## Proposed implementation sequence

1. Review and approve this scope/acceptance proposal.
2. Decide and document minimum-history/time-span gates, forecasting method, and horizon bounds.
3. Implement a pure prediction function with focused tests.
4. Add M12.2 history integration and safe failure handling.
5. Run regression, typecheck, production build, CI, and diff review.
6. Open a PR; do not merge without explicit project-owner approval.
