# M12.2 — Storage History

**Status:** Implementation in progress — isolated branch  
**Branch:** `m12.2-storage-history`  
**Base:** `main` at M12.1 merge commit `5e2e512b372d58bf8f3b8f14222b97aff0bd16ab`

## Scope
- Build a storage-history layer using the validated `StorageSnapshot` model from M12.1.
- Provide add, read, and clear-history operations.
- Reject invalid snapshots and duplicate snapshot IDs.
- Return history in deterministic chronological order (timestamp, then ID for ties).
- Retain a maximum of **100 records** by default; allow a smaller capacity to be injected for deterministic tests. When full, remove oldest records first.
- Safely handle malformed persisted data and storage access failures.
- Add focused unit tests and this scope document.

## Persistence and behavior
- Use one dedicated key: `mobile-freedom-storage-history-v1`.
- Storage is supplied through a small storage interface; the browser adapter uses `localStorage`, while tests use an isolated in-memory implementation.
- Stored history is revalidated when read. Invalid records or duplicate IDs cause fail-closed rejection (empty untrusted history; no automatic repair or deletion).
- Storage read, write, and clear failures do not report success.
- Browser integration is through the dedicated `localStorage` key; no other keys are read or cleared.
- Clear-history removes only the dedicated history key.

## Safety boundaries
- No trend calculations, low-storage warnings, predictions, or confidence estimates (reserved for later M12 sub-milestones).
- No background device monitoring or automatic filesystem scanning.
- No file deletion or mutation.
- No UI changes in M12.2.
- Only explicitly supplied snapshots are recorded; provenance remains visible.
- History persistence is local and limited to a dedicated M12.2 key; clearing history must not affect unrelated storage.

## Acceptance criteria
- Valid snapshots can be added and retrieved in deterministic chronological order.
- Invalid snapshots are rejected using M12.1 validation.
- Duplicate snapshot IDs are rejected.
- Retention capacity is bounded; oldest records are removed deterministically when capacity is exceeded.
- Malformed persisted data is handled safely and never trusted as valid history.
- Clear-history operation removes only the dedicated M12.2 storage key.
- Tests, typecheck, production build, CI, and final diff/safety review must pass.
- Do not mark PASS or merge until verification evidence is available.
